# 바닷바람 탐험과 발견 카드 파일럿

작성: 2026-11-15 · 상태: 사용자 구현 승인, 구현·검증 진행 중

## 목적과 승인 범위

아이디어 제안 중 사용자가 동의한 첫 단계는 바다 미션 한 편과 발견 카드 저장을 연결하는 것이다. 아이가 예상하고, 화면 속 실험의 두 결과를 비교하고, 이유를 알아본 뒤 자신의 탐험 기록을 다시 볼 수 있게 한다. 캐릭터에게 가르쳐주기 대화는 다음 단계다.

사용자는 이 설계 범위의 구현과 직접 볼 수 있는 테스트 환경 준비를 승인했다. 아래 세부 구현 선택은 작성한 설계에 따른다.

## 현재 상태와 실제 변경점

기준은 최신 통합 작업의 소스 커밋 `78bf749`다. 다른 작업의 미커밋 변경은 가져오지 않았다.

- `coast_sail` 팩에는 돛 펼치기/접기, 반대 조건 실험, 비교, 이유 설명, 결말, 카드 저장이 이미 있다.
- `StoryDirector`에는 진행 저장과 복원, 저장 실패 재시도, 중복 요청 방지와 주제별 카드 수집이 있다. 다만 카드는 주제 ID와 고정 문장으로 구성되며 아이의 예상이나 첫 조작을 보존하지 않는다.
- 최신 `UnityAppController`는 `story: null`을 전달한다. `AppUi`도 실험 오버레이를 연결하지 않는다. 이는 직접 대화 화면에서 기존 실험을 분리한 명시적인 설계이며, 미완성 연결로 취급하지 않는다.
- 현재 Pleos 차량 앱에는 이 실험이나 개인 탐험 카드가 연결돼 있지 않다.

따라서 이번 작업은 새 교육 엔진을 만드는 일이 아니라, 별도 수동 진입점을 통해 기존 바다 실험을 다시 연결하고 개인 탐험 기록을 추가하는 일이다. 이전 직접 대화 설계에서 금지한 이야기 버튼 중 이번 바다 파일럿의 수동 진입점만 좁게 재도입하는 제안이다.

## 첫 구현의 경계

구현 대상은 Flutter가 상태를 관리하는 Android Unity 폰 앱이다. Pleos 차량 앱과 서버·Firebase 계약을 바꾸지 않고, 폰에서 한 편을 완주하는 파일럿으로 검증한다. 차량 화면 공유는 후속 설계 대상이다.

차 안 화면의 기존 하단 동작 영역에 `탐험 노트` 진입점 하나를 둔다. 연결된 차 안에서는 바다 미션을 직접 시작하고, 저장된 카드가 있으면 다시 읽거나 재실험한다. 바다 환경 신호가 없어도 `상상 탐험`이라는 안내와 함께 수동 실행할 수 있다. 미연결 최초 화면의 `차량 연결하기` 흐름은 유지한다.

이번 파일럿의 실행 목록은 바다 한 편이다. 기존 다른 7편의 콘텐츠와 저장 카드는 보존하며, 기존 카드는 읽을 수 있지만 다른 팩의 새 실행은 열지 않는다. 자동 초대나 실제 바다·사물 인식은 추가하지 않는다.

## 아이가 경험하는 흐름

1. **시작:** `탐험 노트`에서 `바닷바람 우편배`를 선택한다. 화면 속 배로 해보는 상상 실험임을 알려준다.
2. **예상:** “같은 바람이면 어느 배가 더 멀리 갈까?”에 `돛 펼친 배` 또는 `돛 접은 배`를 선택한다. 정오답 표시 없이 예상을 기억한다.
3. **조작:** “어느 쪽부터 해 볼까?”에서 `돛 펼치기 / 돛 접기`를 고른다. 예상과 첫 조작은 서로 다른 값이다.
4. **비교:** 같은 배·출발점·바람·시간을 유지하고 돛만 바꾼 반대 실험을 본다. 두 결과를 나란히 보여준다.
5. **이유:** “이 실험에서는 돛을 펼친 배가 더 멀리 갔어.” 다음에 “바람이 펼쳐진 돛을 밀어 배를 움직였어.”를 설명한다. 이 파일럿에서는 설명 단계를 건너뛰지 않는다.
6. **기록:** `발견 카드 담기`를 누르면 저장한다. 저장 완료를 확인한 뒤 성공을 안내한다. 실패하면 같은 탐험 기록으로 재시도한다.
7. **다시 보기:** 탐험 노트에서 카드의 예상·첫 조작·관찰 결과·원리와 다음 질문을 읽는다.

발견 카드 예시:

> **바람 우편배**
>
> 내 예상: 돛을 접은 배가 더 멀리 갈 것 같았어.
>
> 먼저 해본 것: 돛 펼치기.
>
> 비교한 결과: 같은 시간 동안 돛을 펼친 배가 더 멀리 갔어.
>
> 알아본 원리: 바람이 펼쳐진 돛을 밀어 배를 움직일 수 있어.
>
> 다음에 생각해 볼 것: 바람으로 움직이는 다른 물건도 있을까?

예상과 결과가 달라도 실패나 감점으로 표시하지 않는다. 관찰과 원리는 작성된 실험 결과이며 AI가 아이의 이해도를 판정한 기록이 아니다. 과학 문안과 아이 대상 가독성은 여전히 검토 대상이다.

## 상태·저장·화면 계약

- Dart의 기존 `StoryDirector`가 실험과 저장의 단일 소유자다. Unity는 표시·조작·진행 요청을 맡는다.
- 예측 선택, 첫 조작, 두 조건의 관찰 완료, 설명 도달 여부를 현재 실행에 기록한다. 자유 발화·음성·대화 원문은 수집하지 않는다.
- 기존 `unityApp.story.v1` 저장 키와 `version: 1`, `cards`, `session`의 의미를 유지하면서 선택적 실행 기록 필드를 추가한다. 필드가 없는 과거 카드는 기존 제목과 원리만 표시한다. 누락된 예상을 추측해 채우지 않는다.
- 개인 기록은 주제 ID별로 마지막으로 성공적으로 저장한 완주 결과 하나를 보관한다. 재실험은 카드 수를 늘리지 않고 성공한 저장에서만 해당 기록을 바꾼다.
- 현재 실행의 예상·조작도 중단 지점과 함께 저장·복원한다. 팩 버전이 달라 과거 세션을 안전하게 이어갈 수 없으면 기존 카드는 유지하고 해당 미완료 실험만 처음부터 시작한다.
- 다른 7편의 과거 미완료 세션은 파일럿의 활성 실행으로 복원하지 않는다. 새 바다 미션 시작을 막지 않으며, 사용자가 바다 미션을 명시적으로 시작하기 전까지 원래 저장본을 유지한다. 시작 시 이전 미완료 실험 대신 바다 미션을 시작한다는 안내를 함께 보여주고 미완료 세션만 교체한다. 과거 발견 카드는 계속 보존한다.
- 카드와 개인 기록은 기존 저장 큐의 같은 쓰기에 포함한다. 저장 실패·처리 중 이탈에서 카드 수나 개인 기록 일부만 성공한 것처럼 보이지 않게 한다.
- 같은 저장 키에는 앱 수명 동안 활성 Director 하나만 쓰기를 소유한다. 화면 이동은 소유자를 교체하지 않는다. 컨트롤러를 재생성해야 할 때는 이전 소유자의 대기 쓰기를 끝내고 종료한 뒤 새 소유자가 읽도록 순서를 보장한다. 이전 소유자의 늦은 쓰기나 새 소유자의 오래된 스냅샷으로 성공한 카드 저장이 사라지지 않아야 한다. 구현 방식은 기존 앱 수명 관리에 맞춰 결정한다.
- 입력은 현재 instance/node/revision과 action ID를 확인한다. 과거 UI의 요청이나 중복 탭으로 새 실험이 진행되지 않게 한다. 파일럿 진입에서는 `coast_sail`만 새로 시작할 수 있다.
- 데이터 준비 전·저장 중에는 해당 조작을 비활성화하되 돌아가기는 가능하다. 초기화 실패 시 재시도 안내를 제공하며 알 돌봄과 직접 대화는 계속 사용할 수 있다.
- 실험/노트가 열린 동안 직접 대화·마이크·알 제스처와 입력을 동시에 소유하지 않는다. 이미 응답 대기 중인 직접 대화나 네이티브 카메라/음성 작업은 취소하지 않고, 끝날 때까지 실험 시작을 막는다.
- 돌아가기, 화면 이동, 백그라운드, 부화/필수 사진 흐름 진입은 실험을 중단·저장하고 입력 소유권을 반환한다. 화면 복귀 시 자동 재개하지 않고 이어 하기를 제공한다.
- 연결 종료는 실험을 일시 중단하고 기존 세션 종료 화면을 우선한다. 저장된 카드는 삭제하지 않는다.
- 기존 스타일·캐릭터·보트 연출을 재사용한다. 새 예상 문장은 자막만으로 진행 가능하게 하고, 기존 음성 파일을 다른 문장에 재사용하지 않는다. 모션 감소에서는 전후 정지 장면으로 비교한다.
- 이전 스토리 미연결 회귀 테스트는 명시적인 파일럿 진입만 허용하도록 갱신한다. 임의 legacy 요청, 자동 초대, 미연결 초기 화면, 다른 팩 실행은 계속 거절한다.

## 수정이 예상되는 영역

`phone/assets/data/window_stories_ko.json`, `phone/lib/story/story_director.dart`, 필요한 최소 팩 모델, `phone/lib/unity_app/unity_app_controller.dart`, Unity의 `AppState`, `AppUi`·하단 진입 UI·`StoryOverlay`와 관련 테스트다. 기존 팩의 안정적 노드 ID는 가능한 한 유지하고, 바다 팩 내용이 바뀌면 해당 팩 버전만 올린다. 저장 필드·UI 배치의 세부 구현은 기존 패턴에 맞춰 구현자가 결정한다.

## 검증과 완료 조건

- 두 예상 × 두 첫 조작의 네 경로가 모두 비교·설명·저장까지 이어지고 각각의 카드 기록이 실제 입력과 일치한다.
- 새 실행·중단 복원·앱 재시작, 과거 카드/다른 팩의 미완료 세션 로딩, 저장 실패/재시도, 재실험 시 기록 교체, 지연 쓰기 중 이탈과 컨트롤러 교체를 검증한다.
- 앱에서 실제 수동 진입·돌아가기·이어 하기와 Unity→Dart→Unity 상태 왕복을 확인한다. 별도 Director 테스트 통과만으로 연결 완료라고 하지 않는다.
- 자동 초대 없음, 다른 7편 새 실행 차단, 기존 카드 보존, 알 돌봄/직접 대화/사진/부화 흐름 회귀를 확인한다.
- 관련 Flutter 및 Unity 테스트를 실행하고 Android Unity 화면에서 예상·비교·카드·저장 실패를 확인한다. 가로 소형 화면에서도 버튼과 한국어 문구가 잘리지 않아야 한다.
- 테스트·에뮬레이터 관찰·실기기/실차 검증 결과를 구분해 기록한다. 원격 배포·PR 병합·APK 배포는 이 설계에 포함하지 않는다.
