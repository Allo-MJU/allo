# ALLO 기능 개편 상세 명세 초안

> 작성일: 2026-11-09 · 상태: 팀 검토 전 제안 · 코드 기준: `ebb979a44ea4bae5d91728a7865664185e188159`
>
> 차량 낚시 대기 화면과 폰 이동, 대화 기반 호감도 부화, 차량 거점과 캐릭터 역할, 캐릭터의 여행 부탁을 다룬다. 3D 모델링·리깅·3D 렌더러 도입은 제외한다. **이 문서의 규칙·수치·필드 이름은 구현 검토를 위한 제안이며, 기존 계약을 확정 변경하거나 구현 완료를 선언하지 않는다.**

## 1. 목적과 적용 범위

시간을 기다려 알을 얻는 흐름에 대화와 관계 형성을 더하고, 부화한 캐릭터가 거점에서 역할을 수행하며 다음 여행을 제안하도록 한다. C는 게임 규칙과 상태·데이터 계약을 담당한다. A와 B는 각 기기의 입력·출력·저장·통신에 연결하고, D는 필요한 2D 아트와 연출 자산을 제작한다.

이 문서는 기능별 정상 흐름, 상태 전이, 계산 규칙, 저장·동기화, 실패 처리, 코드 변경 지점과 검증 조건을 함께 제시한다. 팀이 규칙을 선택하면 해당 부분을 `schema.md` 등 공식 계약에 반영한 뒤 구현한다.

| 구분 | 내용 |
| --- | --- |

| 요청된 방향 | 기존 시간 측정 방식을 유지하되, 제한 안에 대화로 호감도를 채워야 알이 부화한다. 실패 결과는 깨짐 또는 도망이다. |
| 요청된 방향 | 목적지·오늘의 기분·여행에 대한 기대를 이야기하는 경험을 제공한다. |

교육 효과와 여행 계획 습관 형성은 기대효과다. 대화 3회를 완료했다고 실제 이해도나 교육 성과가 확인된 것으로 기록하지 않는다.

### 1.3 기존 문서와의 관계

- [schema.md](schema.md)는 현행 통신·저장 계약이며 이 초안보다 우선하는 **현재 구현 기준**이다. 합의 전에는 이 초안만 보고 원격 필드를 추가하지 않는다.
- [ai-dialogue-design.md](ai-dialogue-design.md)는 팀 검토 전 초안이며 정해진 질문 선택·원문 비저장을 전제로 한다. 이번 자유 발화 입력은 그 전제를 바꾸는 제안이다. 실제 입력 처리 위치와 대사 정책을 함께 갱신해야 한다.
- [dev-plan.md](dev-plan.md)의 A/B/C/D 분담은 유지한다. 공유 파일의 수정 담당은 9절처럼 작업 단위로 한 명씩 정한다.
- 주행 중 화면은 현재 알과 진행률로 제한되어 있다. 요청된 낚시 장면은 이 정책의 변경을 포함한다. 실제 차량에서 허용되는 표시 범위는 A가 확인한다. 확인 전 정차·가짜 신호 시연은 구현 검증 단계이며, 주행 중 사용 가능성을 입증하지 않는다.

## 3. 공통 실행 원칙

### 3.1 판정과 표시의 주인

- 게임 판정의 실행 위치는 폰이다. `allo_core`는 순수 규칙을 계산하고 컨트롤러가 입력·저장·발행을 조정한다. C가 별도 서버를 새로 운영해야 한다는 뜻이 아니다.
- 차량은 입력 요청과 차량 신호를 보낸다. 부화 성공·실패, 호감도, 캐릭터 소유권을 차량이 독립적으로 계산하지 않는다.
- `/game`은 계속 폰 단일 작성자다. 차량이 이동 처리 편의를 위해 `/game` 일부를 쓰지 않는다.
- 알 상태, 선택한 동행 캐릭터, 거점 작업, 여행 부탁은 서로 다른 상태다. 한 개의 `stage`에 전부 합치지 않는다.
- 성공 결과는 로컬 저장 후 표시·원격 발행한다. 네트워크 재시도 때문에 보상·획득·완료가 두 번 적용되지 않게 결과 ID로 중복을 막는다.

### 3.2 시간과 ID

| 값 | 용도 | 단위·범위 |
| --- | --- | --- |
| `eggId` | 알 회차와 부화 결과 식별 | 알 지급 때 생성·저장, 재시작·차량 재연결 시 유지 |
| `creatureId` | 획득한 개체 식별 | 성공한 `eggId`에 대응하는 영속 ID, 같은 종끼리도 다름 |
| `speciesId` | 종 카탈로그 조회 | 기존 종 ID 유지 |
| `turnId` | 발화 제출 1건의 중복 방지 | 입력 시작 때 생성, 재시도 콜백에 원래 ID 유지 |
| `requestId` | 차량→폰 이동 요청 | 같은 요청 재전송 시 동일 ID |
| `gameRevision` | 전체 원격 스냅샷 순서 | 같은 세션에서 단조 증가, 발행 전에 로컬에 저장 |
| `taskId`, `wishId` | 거점 작업·여행 부탁 | 생성 후 완료·취소까지 유지 |
| `activeElapsedMs` | 알·거점 작업의 인정 진행 | 단조 시계 누적 밀리초, 앱 중단 제외 |
| `lastConfirmedAtMs` | 여행 부탁 간격 | epoch ms, 실제 시간 경과용이며 부화 시계와 별개 |

세션이 바뀌어도 개체·거점·부탁은 폰에 남는다. 이동 요청·차량 화면 점유는 세션 범위다. 이전 세션 이벤트나 이전 연결의 비동기 결과를 새 세션에 적용하지 않는다.

## 4. 기능 1 차량 낚시 대기 화면과 폰 이동

### 4.1 범위와 진입

낚시는 캐릭터가 쉬는 대기 연출이다. 물고기 획득, 낚싯대 강화, 재화 보상은 이 기능에 포함하지 않는다. 캐릭터를 부르면 낚시를 멈추고 폰에서 기존 터치·놀이·먹이 같은 상호작용을 이어간다.

표시 대상은 폰에서 선택한 **이미 부화한 보유 개체**다. 최초 사용으로 보유 캐릭터가 없으면 알 대기 화면을 보여주며 호출 버튼·명령에는 아직 부를 캐릭터가 없다고 응답한다. 새 알을 품는 동안에도 기존 개체를 선택할 수 있다. `game.speciesId`를 새 알의 종과 동행 개체 ID 양쪽에 재사용하지 않는다.

차량 연결 시 폰은 선택한 개체와 표시 상태를 발행한다. 새 세션의 기본 위치는 `car`로 제안한다. 같은 세션의 재연결에서는 마지막으로 저장된 위치를 복원한다. 보유 개체 삭제/손상으로 선택이 무효라면 다른 개체를 임의 생성하지 않고 선택을 해제한다.

### 4.2 정상 흐름

1. 차량은 연결된 폰의 `companion.location=car`를 읽고 캐릭터 낚시 장면을 표시한다.
2. A의 음성 명령 처리기가 호출 의도를 받는다. 추가 Gleo 명령 지원은 검증 대상이며 현재 등록된 3개 명령과 별개로 확인한다.
3. 차량이 `companionTransferRequested` 이벤트에 `requestId`, `displayId`, `displayRevision`, `target=phone`을 담아 보낸다. `displayId`는 폰이 로컬 개체와 연결해 둔 임시 표시 ID다.
4. 폰은 활성 세션·선택 개체·표시 세대·현재 위치·중복 ID를 확인한다. 처리가 불가능하면 이유를 포함한 결과를 발행한다.
5. 폰은 위치 변경과 요청 처리 결과를 같은 로컬 저장 단위에 기록하고 `location=phone`, 증가한 `displayRevision`, 독립된 `transferResult`를 전체 `/game`에 반영한다.
6. 차량은 일치하는 결과를 수신한 뒤 퇴장 연출을 하고 ‘폰에서 함께하고 있음’을 표시한다. 폰은 진입 연출을 한 번 재생한다.
7. 이후 상호작용은 폰의 기존 입력 기능으로 수행한다. 부화 판정이나 알 제한시간은 화면 이동 때문에 초기화·일시정지되지 않는다.

요청 전송만으로 차량의 캐릭터를 먼저 지우지 않는다. 퇴장·진입 애니메이션의 프레임 동기화는 요구하지 않으며, **논리적으로 하나의 표시 위치**를 공유한다. 통신이 끊기면 두 화면에 잠시 같은 그림이 남을 수 있으므로 연결 상태를 표시하고 재연결 시 스냅샷으로 맞춘다.

### 4.3 상태와 반환

```text
car ── 유효한 호출 + 폰 저장 성공 ──> phone
phone ── 폰에서 차로 돌려보내기 + 저장 성공 ──> car
선택 없음 ── 보유 개체 선택 ──> car 또는 phone
세션 종료 ──> 원격 표시 종료, 로컬 개체·선택 기록 유지
```

`requesting`은 차량의 임시 UI 상태다. 저장된 위치와 별도로 둔다. 반환 버튼은 기본 제안이며 첫 구현에서 제외할 경우 새 세션에서만 차량 위치로 초기화하는 제한을 명시한다. 폰에서 거점 작업 중인 개체를 직접 선택/호출하면 `busy`로 거절한다. 차량의 오래된 표시 ID 요청은 개체의 작업 상태를 보기 전에 `staleSelection`으로 거절한다. 사용자가 작업을 취소한 뒤 다시 선택·호출할 수 있다.

### 4.4 실패와 재연결

| 조건 | 처리 |
| --- | --- |
| 폰 미연결·앱 미실행 | 차량은 연결 안내, 위치 변경 없음. 앱을 원격으로 강제 실행하는 기능은 전제하지 않는다. |
| 마이크/음성 명령 불가 | 폰에서 `불러오기`를 제공. 실제 음성 호출 완료와 수동 시연을 구분한다. |
| 요청 후 10초 내 결과 없음 | 차량은 `확인 지연` 표시. 실패 확정·새 ID 자동 발급 없이 현재 `/game` 재확인. |
| 같은 ID 재수신 | 해당 세션의 확정 처리 기록이 있으면 같은 결과 재발행, 이동·진입 연출 반복 없음. 미확정이면 현재 유효성을 다시 판단. |
| 이미 폰에 있음 | `alreadyOnPhone`으로 종료, 성공적인 최종 위치는 그대로. |
| 다른 개체·이전 표시 세대 | `staleSelection`, 현재 선택 상태를 다시 읽는다. |
| 저장 실패 | 폰에 저장 오류 표시, 위치·확정 결과 발행 없음. 차량은 확인 지연으로 남고 같은 요청 ID로 재시도. |
| 세션 종료·교체 | 이후 이동 결과와 지연 콜백 무효. 세션 종료가 표시 전환보다 우선. |

이벤트 `ts`만으로 두 기기의 정확한 시계 일치를 가정하지 않는다. 폰의 세션 연결·앱 복귀·통신 재연결 때는 위치를 복원하되 새 `displayId`를 저장·발행한 뒤 요청 소비를 연다. 이전 표시 ID의 미처리 요청은 실행하지 않는다. 선택 교체 때도 표시 ID를 바꾼다. 같은 연결 안에서 10초를 넘겨 도착한 결과는 여전히 유효할 수 있으므로 `확인 지연`을 취소 완료로 표시하지 않는다. 차량 요청 대기는 1개로 제한하고, 오프라인 요청을 새 연결에 자동 복제하지 않는다.

처리 우선순위는 `종료/다른 세션 거절 → 같은 requestId의 확정 기록 반환 → 표시 ID·요청 revision 검사 → busy 검사 → 현재 위치 검사 → 새 결과 저장`이다. 처리 기록에는 `sessionId`, `requestId`, 요청 당시 `displayId/revision`, 결과 상태·결과 위치를 저장한다. 저장 후 발행 전에 앱이 꺼졌다면 새 표시 ID 발급과 관계없이 **이미 처리된 요청의 기록**을 재발행한다. 미처리된 이전 표시 ID만 폐기한다. 확정 기록은 해당 세션 최종 저장까지 보관한다.

차량은 `transferResult` 안의 요청 ID와 요청 당시 표시 ID/revision으로 응답을 찾는다. 현재 `companion`이 선택 해제로 없어져도 거절 결과를 표현할 수 있도록 결과는 최상위 독립 필드다. `saveFailed`는 확정 결과 코드로 저장하지 않는다. 저장이 다시 가능해진 동일 연결에서는 같은 ID로 재시도하고, 재연결로 표시 ID가 바뀌었다면 미처리 요청은 거절한 뒤 사용자의 새 호출로 진행한다.

`game.ts`는 연결 생존 신호가 아니다. 기존 게임은 유휴 상태에서 쓰기 간격이 길 수 있으므로, A/B는 연결·재연결 알림과 새 루트 스냅샷 수신을 별도로 전달해야 한다. 부화 연출 중 이동이 완료되면 폰은 결과 상태를 보관하고 부화 화면을 끝낸 뒤 동행 영역을 표시한다. 화면 이동 이벤트가 부화 결과 저장이나 종료 화면을 강제로 우회하지 않는다.

## 5. 기능 2 대화 기반 호감도 부화

### 5.1 기존 시간표 유지

| 알 지급 시 조건 | 기존 계산을 유지한 품기 마감 | 이후 구간 |
| --- | --- | --- |
| ETA 120~4800초 | `floor(ETA / 120) * 60`초 | 남은 시간은 동행 또는 실패 결과 구간 |
| ETA 4800초 초과 | 2400초 | 1800초 후 반복 조건에 따라 다음 알 |
| ETA 없음 | small 5km / mid 25km / large 75km | 시간 초과 개념 대신 해당 거리 경계에서 판정 |
| ETA 120초 미만 | 새 알 지급 보류 | 현재 동행 유지 또는 첫 알 없이 대기 |

예: ETA 11분은 품기 5분+이후 6분, 80분은 40+40분, 81분은 첫 회차 40+30분 후 당시 ETA로 다음 알을 판단한다. 알 지급 뒤 ETA가 바뀌어도 해당 알의 마감은 다시 계산하지 않는다. 앱 중단 중 시간·거리·주행 조작을 더하지 않는 기존 정책도 유지한다.

거리 모드는 남은 시간을 임의로 환산해 표시하지 않는다. 목표 지점까지 호감도를 채운다는 의미다. 기존 `progress`는 계속 시간/거리 진행도이며 호감도 진행도와 다른 값이다.

### 5.2 대화 흐름과 판정 입력

1. 폰 품기 화면에 남은 시간/거리, 호감도, 세 대화 주제를 보여준다.
2. 아이가 주제를 고르고 짧게 말한다. 예: `destination` 어디로 가는지, `mood` 지금 기분, `expectation` 오늘 기대하는 일.
3. B의 입력 계층이 음성을 받아 인식 결과를 확인할 수 있게 한다. C의 입력 판정 계층은 유효한 답변 제출을 구조화된 결과로 만든다.
4. 코어는 `AcceptedTurn(eggId, turnId, topic)`을 받아 점수를 갱신한다. 문자열 원문으로 직접 상태를 변경하지 않는다.
5. 폰은 답변을 받았다는 짧은 반응과 호감도 변화를 보여준다. 목적지의 역사·교육 정보를 사실처럼 생성하는 기능은 별도 요구로 둔다.
6. 세 주제를 완료하면 준비 완료로 표시하고 기존 품기 마감까지 기다린다.

**유효 답변 기본안:** 선택한 주제에 대해 입력이 완료되고 비어 있지 않은 최종 인식 결과를 사용자가 제출했을 때 인정한다. 조용히 있었거나 취소·인식 오류·중간 결과인 경우 인정하지 않는다. 기본안은 내용의 진실성·어휘 수준·주제 적합성을 자동 평가하지 않으며, 짧은 대답과 부정적인 기분도 동일하게 인정한다. 의미를 이해하고 대화했다고 주장하려면 별도 해석기와 평가 기준이 필요하다.

음성 처리 제공자·모델·처리 위치는 미선정이다. 기본 요구는 원문과 녹음을 영속 저장하거나 게임 동기화에 보내지 않는 것이다. 실제 음성 SDK가 외부 전송을 하는지는 선택 시 확인해야 하며 ‘온디바이스 처리 완료’로 가정하지 않는다. 개발용 입력 어댑터와 텍스트 대체 입력은 규칙 검증용이며 실제 음성 동작 검증을 대신하지 않는다.

### 5.3 호감도 규칙

| 입력 | 점수·결과 |
| --- | --- |
| 아직 완료하지 않은 주제의 첫 유효 답변 | +1, 해당 주제 완료 기록 |
| 이미 완료한 주제의 다른 답변 | 0, 대화 반응은 가능 |
| 동일 `turnId`의 중복 결과 | 0, 기존 결과 반환 |
| 다른 `eggId`, 중단 전 입력 세대, 알 수 없는 주제 | 반영하지 않음 |
| 녹음 시작·질문 재생·버튼만 누름 | 0 |
| 목표 3점 달성 | `ready`, 즉시 부화하지 않음 |
| 마감 시 3점 | 성공 결과 저장 → 부화·도감 등록 |
| 마감 시 0~2점 | 실패 결과 저장 → 깨짐 또는 도망 연출 |

`affinityScore = completedTopics.length`, `affinityTarget = 3`으로 계산한다. 점수를 별도로 가산해 주제 수와 불일치하게 만들지 않는다. 점수와 목표는 알 지급 시 선택한 `ruleVersion`으로 고정한다. 기존 `careCount`의 희귀도 보정은 유지하며, 호감도가 높다고 종·등급을 임의로 높이지 않는다.

### 5.4 상태 전이와 경계

```text
incubating(open, 0~2점) ── 세 주제 완료 ──> incubating(ready, 3점)
incubating ── 기존 마감 도달 ──> 결과 저장 대기
결과 저장 대기 ── 3점 결과 저장 성공 ──> hatched
결과 저장 대기 ── 0~2점 결과 저장 성공 ──> failed
저장 실패 ──> 같은 결정 결과 재시도, 새 알 지급 보류
```

시간 모드에서는 **최종 제출 결과를 컨트롤러가 처리하는 시점**의 활성 경과가 마감보다 작아야 인정한다. 정확히 마감과 같으면 기한 밖이다. 발화 시작이 빨랐어도 STT 완료가 늦으면 반영하지 않는 기본안이다. 느린 인식이 불리할 수 있으므로 실제 지연을 확인하고 결정 D03에서 유예 여부를 정한다. 이 문서는 임의의 숨은 유예시간을 넣지 않는다.

컨트롤러는 대화 결과·차량 샘플·세션 종료를 직렬 처리한다. 대화 결과마다 활성 시계를 먼저 갱신하고 이미 마감이면 결과를 확정한 뒤 대화를 거절한다. 거리 모드는 처리된 차량 샘플의 순서를 기준으로 하며, 미수신 구간의 실제 차량 위치 순서를 보장하지 않는다.

성공한 알의 종·등급 선정에는 마지막 정상 차량 스냅샷과 해당 알의 누적 판정 데이터를 사용한다. 새 스냅샷을 임의 생성하지 않는다. **호감도 미달은 종 선정 없이 실패 결과를 저장한다.** 목표를 달성했지만 종 선정에 필요한 데이터가 전혀 없다면 `resultPending`으로 두고 복구 가능한 오류를 표시한다. 신호 공백으로 지나간 여러 알을 소급 생성하지 않는다.

### 5.5 실패 후 동작과 중단

- 실패는 해당 알에만 적용한다. 이미 얻은 캐릭터와 거점은 유지한다. 아직 생성되지 않은 생물을 소유 목록에서 삭제하는 처리도 없다.
- 깨짐과 도망 중 어떤 연출을 쓸지는 D06에서 결정한다. 둘을 동시에 발생시키거나 실패 문구로 아이를 비난하는 표현을 기본값으로 넣지 않는다.
- 반복 알 회차는 원래 다음 알 시점에 같은 크기 알 1개를 지급한다. 실패 즉시 재지급하지 않는다. 예: 40분에 실패하면 첫 회차의 70분 시점에서 당시 ETA로 재지급 여부를 판단한다.
- 마지막 시간 회차와 거리 모드는 해당 주행에서 자동으로 새 알을 만들지 않는다. 저장된 실패 결과를 닫은 다음 주행에서 기존 새 알 시작 흐름을 따른다. 수동 즉시 재도전은 별도 결정이다.
- 마감 전 차량 최종 종료는 실패가 아니다. 인정된 시간·거리·완료 주제를 저장하고 다음 주행에서 이어한다. 최종 차량 샘플 적용으로 마감을 넘으면 그 알의 결과를 저장한 뒤 종료한다.
- 앱 중단 시 녹음·인식 작업을 취소하고 입력 세대 번호를 바꾼다. 복귀 뒤 늦게 도착한 취소 전 결과를 새 입력으로 채택하지 않는다.
- 목표를 채운 뒤 앱을 꺼도 기존처럼 활성시간은 멈춘다. 실제 시계만 흘렀다는 이유로 실패·부화를 처리하지 않는다.

`failed`에서도 결과 저장이 끝나면 해당 회차의 활성 경과와 `companionEndSec/grantsNextEgg` 계획을 유지한다. 실패 화면을 닫는 동작은 결과 확인만 의미하며 시계를 초기화하거나 알을 지급하지 않는다. `_grantNextEgg` 호출·허용 조건을 `hatched`와 저장 완료된 `failed` 양쪽으로 확장한다. 기존 다음 알 경계에서 최신 ETA를 확인해 한 번만 지급하고, 새 알을 저장하기 전에 이전 실패 회차의 종료 기록을 보관한다.

일시중단 뒤에는 같은 실패 회차와 다음 알까지 남은 활성 구간을 복원한다. 차량의 최종 종료를 저장한 경우에는 완료된 성공/실패 회차를 닫고, 다음 주행에서 새 알 시작 조건을 평가한다. 아직 품기 중인 회차만 기존 진행을 이어간다. 최종 종료와 다음 알 지급이 겹치면 종료가 우선하므로 마지막 순간에 새 알을 만들어 저장하지 않는다.

### 5.6 저장과 기존 사용자

결정 결과를 `eggId`에 고정해 먼저 저장하고, 성공이면 같은 `creatureId`로 도감을 추가한 뒤 적용 완료를 기록한다. 저장 중 재실행되어도 종을 다시 추첨하거나 같은 알을 두 번 획득하지 않는다. 원격 부화 이벤트와 성공 연출은 로컬 결과 적용 이후에 발생한다.

기존 진행 중 알에 새 호감도 요구를 갑자기 적용하면 마감 직전 복귀한 사용자가 실패할 수 있다. **기본 이행안은 이미 지급된 알 1개만 기존 시간 기반 규칙으로 마무리하고, 다음 알부터 새 `ruleVersion`을 쓰는 것**이다. 완료된 도감·기존 부화 결과는 보존한다. 데이터 손상을 기존 버전으로 임의 해석하지 않는다.

## 6. 기능 3 차량 거점과 캐릭터별 역할

### 6.1 거점과 소유 모델

첫 구현은 **폰 한 대에 거점 하나**를 둔다. 차량은 거점을 보여주는 공간이고, 실제 저장은 폰이 소유한다. 다른 차량에 페어링해도 같은 거점을 사용한다. 가족 여러 폰의 공동 거점이나 계정 간 동기화는 이번 범위에 포함하지 않는다.

거점에는 건설·요리·훈련 영역을 하나씩 두고, 해당 역할 개체를 획득해야 활동이 열린다. `소유`는 도감 저장이 성공한 개체를 의미한다. 품기 중인 알이나 결과 저장 대기 중인 종만으로는 콘텐츠를 열지 않는다.

역할은 `speciesId → roleId` 콘텐츠 표로 정의한다. 속성과 역할은 독립이다. 물 속성이 반드시 요리 역할이라는 규칙을 코드에 하드코딩하지 않는다. 종별 역할 매핑은 C·D가 정하며, 입력이 없는 종은 `roleId=null`로 처리하고 기본 동행에는 사용할 수 있다.

| 예시 역할 | 검토용 종 배정 예시 | 해금되는 첫 활동 |
| --- | --- | --- |
| `builder` | 길싹이 `road_sprout` | 고정된 거점 슬롯에 쉼터 만들기 |
| `cook` | 웅덩이삐약 `puddle_pip` | 메뉴를 골라 식탁에 요리 놓기 |
| `trainer` | 등불나방 `lamp_moth` | 다른 보유 캐릭터에게 인사 동작 가르치기 |

위 세 종 배정은 확정이 아니다. 비·밤 또는 특정 신호 지원에만 역할이 몰리면 사용자가 콘텐츠를 열기 어렵다. 기존 획득 조건을 보존하면서 역할별 접근성을 점검하고 배정을 결정한다. 시연용 강제 지급은 별도 Fake 프로필에서만 사용한다.

### 6.2 진입과 조작

1. 페어링 전이나 주행 종료 후에도 폰 홈에서 거점을 연다.
2. 잠긴 영역은 필요한 역할과 현재 도감의 획득 힌트를 보여준다.
3. 해당 역할을 가진 보유 개체를 선택해 영역에 배치한다. 같은 역할의 다른 개체로 교체할 수 있다.
4. 가능한 활동과 결과를 확인하고 시작한다.
5. 캐릭터의 작업 연출과 남은 진행을 표시한다. 완료 결과 저장 후 거점 외형이나 캐릭터 동작이 바뀐다.
6. 앱 재실행·새 차량 세션에서도 결과를 다시 볼 수 있다.

차량에 표시할 거점은 정차 화면을 기본으로 제안한다. 주행 중 낚시 대기와 거점 전체 화면은 다른 표현이다. 거점 조작 버튼을 차량 주행 화면에 그대로 옮기지 않는다.

폰의 홈·거점·부탁 화면은 `paired`나 `Stage.hatched`를 진입 조건으로 사용하지 않는다. 로컬 프로필이 준비되면 열 수 있다. 차량 종료 저장 중에는 기존 종료 화면을 우선하지만 저장 완료 후에는 `/home`, `/base`, `/wishes`를 허용하도록 라우터의 종료 후 허용 목록을 확장한다. 종료 실패 상태에서는 먼저 재시도·복구를 처리한다.

### 6.3 역할별 최소 동작

세 활동 모두 **활성 진행 30초**를 검토용 기본값으로 둔다. 앱이 활성 상태인 동안 진행하고 중단 중에는 멈춘다. 사용성 확인 뒤 활동별 시간이나 직접 조작 방식으로 바꿀 수 있다. 재화·재료·스태미나·경험치를 추가하지 않아도 결과를 확인할 수 있게 한다.

| 활동 | 시작 조건 | 완료 효과 | 재실행 |
| --- | --- | --- | --- |
| `build_shelter` | builder 배치, 쉼터 슬롯 비어 있음 | `builtStructureIds`에 `rest_shelter` 추가, 거점에 쉼터 표시 | 이미 지었으면 재시작 불가. 중복 완료로 두 개를 만들지 않음. |
| `cook_meal` | cook 배치, 지원 메뉴 선택 | `lastMealId` 갱신, 식탁의 요리와 반응 표시 | 다른 요리 또는 같은 요리로 다시 실행 가능. 재고를 누적하지 않음. |
| `teach_greeting` | trainer 배치, 다른 보유 개체 선택, 대상이 해당 동작 미습득 | 대상 개체의 `learnedActionIds`에 `greeting` 추가 | 같은 대상·같은 동작은 재실행 불가. 습득 동작은 동행/거점에서 재생 가능. |

요리 메뉴는 첫 콘텐츠로 2개 이내를 제안하며 정확한 이름과 아트 키는 C·D가 정한다. 훈련은 전투 능력·레벨 증가로 연결하지 않는다. 역할별 결과가 실제 화면에 연결되어야 완료이며, 카운터만 증가하는 상태를 기능 완료로 보지 않는다.

### 6.4 작업 상태와 충돌

```text
idle → running → completed
           └── 명시적 취소 → cancelled
running → 앱 중단 → 같은 running 상태와 진행량 저장 → 복귀 후 계속
완료 저장 실패 → completionPending → 같은 결과 재시도
```

- 첫 구현은 거점 전체에서 진행 작업 1개만 허용한다. 병렬 작업 슬롯은 후속 확장으로 둔다.
- 배치와 작업은 다르다. 영역에 배치되어 있어도 작업하지 않으면 동행 개체로 선택할 수 있다.
- 작업의 수행 개체와 훈련 대상은 `busy`다. 동행 호출·역할 교체·다른 작업 배정을 거절한다. 진행 작업을 명시적으로 취소한 뒤 변경한다.
- 시작 전 해당 개체가 차량 또는 폰의 활성 동행이면, 폰에서 ‘거점에서 일하게 하기’를 선택해 동행 선택을 해제한다. 이 선택은 이동 대기를 무효화하고 표시 ID를 바꾼다. 작업 시작을 눌렀다는 이유로 차량 표시를 조용히 빼앗지 않는다.
- 취소하면 이번 미완료 효과를 적용하지 않는다. 재시작은 0부터이며 기존 완성 구조물·요리·습득 동작은 보존한다.
- 시작 시 `taskId`, 역할·개체·대상·활동·필요시간·정책 버전을 저장한다. 업데이트로 콘텐츠 수치가 바뀌어도 실행 중 작업의 소요시간은 유지한다.
- 완료 처리와 표시 사이에 앱이 종료되어도 같은 `taskId` 효과를 한 번만 적용한다. 저장 실패는 완료 효과를 다시 추첨·생성하지 않고 같은 결과를 재시도한다.

거점 작업의 시계는 차량 샘플이나 알의 `_onVehicle`에 종속시키지 않는다. 프로필이 준비되고 실행 작업이 있으며 앱이 활성일 때 폰의 단조 시계 기반 타이머를 실행한다. 화면 갱신·완료 검사는 1초 간격을 기본으로 하되 진행은 tick 횟수가 아닌 실제 인정 시간 차이로 계산한다. 중단 시 경과를 확정·저장하고 타이머를 멈춘다. 복귀 시 새로운 시계 기준점부터 계속해 백그라운드 경과를 합산하지 않는다.

작업 시작·취소·완료와 앱 중단 때 저장하고, 실행 중에는 5초마다 진행 체크포인트를 저장하는 기본안이다. 마지막 저장 전 강제 종료된 진행은 유실될 수 있지만 완료 효과를 중복 적용하지 않는다. 차량 최종 종료 자체가 거점 작업을 취소하지 않으며, 종료 저장을 먼저 마친 뒤 동일한 로컬 작업을 계속한다. 완료 저장 실패는 타이머를 멈춘 `completionPending`으로 고정해 재시도한다.

### 6.5 해금과 데이터 복구

해금 여부는 현재 소유 개체와 역할 표에서 계산한다. `builderUnlocked=true` 같은 중복 원본을 따로 저장하지 않는다. 필요하면 화면용 캐시를 쓰되 소유 기록에서 다시 계산할 수 있어야 한다.

배치된 ID가 도감에 없거나 역할 표가 바뀐 경우 해당 배치를 무효화하고 다시 선택하게 한다. 이미 완성된 거점 결과는 보존한다. 수행 개체를 찾지 못하는 실행 중 작업은 `blocked`로 보여주고 재배치 또는 취소를 요구한다. 손상된 도감을 빈 도감으로 덮어쓰지 않는다.

## 7. 기능 4 캐릭터의 다음 여행 부탁

### 7.1 추천의 의미

아이와 부모가 다음 여행을 생각할 계기를 만드는 기능이다. 이미 설정된 목적지와 현재 내비 경로를 자동 변경하지 않는다. 부탁을 보거나 사진을 첨부하지 않았다고 호감도·캐릭터 소유·부화 확률을 낮추지 않는다.

예시 대사:

> 파도 소리가 듣고 싶어. 다음에는 바다에 가보면 어때? 가게 되면 네가 본 바다를 나한테도 보여줘!

폰의 부탁 카드에는 `부모에게 보여주기`를 둔다. 차량 연결 없이 같은 폰에서 캐릭터의 부탁·대상 지역·다음 여행으로 보관하는 선택을 크게 보여주는 화면이다. 메시지를 자동 전송하거나 부모에게 알림을 발송하지 않는다. 부모가 함께 읽고 계획 여부를 선택할 수 있도록 한다.

바다를 다녀왔다고 확인한 기록이 있으면 ‘다시 가보고 싶어’라고 말할 수 있다. 기록이 없으면 ‘가보고 싶어’라고 표현한다. 기록 부재를 실제 미방문으로 단정하지 않는다. 물 속성의 취향은 캐릭터 설정이며 실제 어머니나 가족과 헤어졌다는 서사를 추가하지 않는다.

### 7.2 속성과 취향

기본 예시는 `attribute=water → preferredRegion=coast`다. 기존 날씨 기반 속성 판정을 재사용한다. ‘비 오는 날 태어났다’는 표현은 게임이 비 태그로 판정했다는 설정이며 실제 기상 정보를 검증했다는 뜻은 아니다.

`normal/dark`와 다른 지역의 매핑은 콘텐츠 결정 사항이다. 첫 구현에서 매핑이 없는 개체는 자동 부탁 대상에서 제외하고 동행·거점에는 그대로 사용할 수 있다. 종별 예외 취향을 두려면 종 데이터의 명시값이 속성 기본값보다 우선하도록 한다.

시연·Fake 기록은 실사용 프로필과 분리한다. 기존 도감은 개체와 속성은 보존하되 자동 부탁 대기 기준을 기능 활성화 시점 이후로 잡아 업데이트 직후 많은 부탁이 한꺼번에 나타나지 않게 한다.

### 7.3 부탁 생성 규칙

순수 규칙 함수는 현재 시각과 저장 데이터를 입력받는다. 자체 네트워크 조회·GPS·AI 호출은 하지 않는다. 평가는 폰 홈/거점을 열 때와 주행 종료 저장 후 수행한다. 백그라운드 상시 실행이나 푸시 알림은 첫 구현에 포함하지 않는다.

```text
baseline = max(개체 획득 시각, 기능 활성화 시각, 대상 지역 최근 방문 확인 시각)
eligible = 선호 지역 있음
           AND 현재 시각 >= baseline + 7일
           AND 해당 지역 재요청 가능 시각 도달
           AND 진행 중 부탁 없음
```

여기서 7일은 여행 빈도 관찰 전 제안값이다. 가족이 어디에 갔는지 모르는 기간을 ‘바다에 안 간 기간’으로 확정하지 않고, 마지막 확인 이후 시간이 지났다는 조건으로만 쓴다. 기기 시계가 뒤로 갔으면 생성을 보류하고 음수 기간을 7일 경과로 처리하지 않는다. 시계가 앞으로 크게 변경되면 빨리 생길 수 있는 기기 로컬 시간의 한계는 남으며 부화 시계에는 영향을 주지 않는다.

후보가 여럿이면 가장 오래 기다린 개체부터 선택하고 동률은 `creatureId`의 고정 정렬 순서로 정한다. 진행 중 부탁은 기기 전체 1개다. 부화 저장 대기 중인 개체, 손상된 소유 기록, 역할 작업 수행 중인 개체는 새 부탁 후보에서 제외하고 다음 평가 때 다시 확인한다.

### 7.4 부탁 상태

| 상태 | 사용자 행동·조건 | 다음 상태·효과 |
| --- | --- | --- |
| 없음 | 생성 조건 충족 | `offered`, 새 `wishId`와 대상 개체·지역 저장 |
| `offered` | 다음에 가보고 싶어 | `planned`, 다음 여행 카드로 보관 |
| `offered/planned` | 나중에 | `snoozed`, 같은 부탁을 24시간 숨김 |
| `snoozed` | 24시간 후 앱 진입 | 보류 전 상태로 복귀, 새 ID 생성 없음 |
| 진행 중 | 부탁 닫기 | `dismissed`, 같은 지역 새 부탁은 14일 후 가능 |
| 진행 중 | 해당 지역에 다녀왔어 확인 | `completed`, 방문 확인 시각과 추억 카드 저장 |
| `completed` | 사진 추가·삭제 | 완료 유지, 로컬 사진 연결만 변경 |

완료 후에도 같은 지역 새 부탁은 14일 이후로 제안한다. `snoozed`도 진행 중 부탁 수 1개에 포함한다. 이미 완료·닫힌 부탁을 재전송된 입력으로 다시 열지 않는다. 앱 재실행·차량 세션 교체는 부탁 상태를 초기화하지 않는다.

### 7.5 방문 확인과 사진

현재 `DexEntry.regionTag`는 **알 품기 중 우세하게 관측한 지역**이고 실제 방문 일지가 아니다. `uncollectedRegions`도 수집 요약이다. 이 둘로 최근 바다 방문 날짜를 만들지 않는다. 내비 요청 성공, ETA 0, 기어 P, `sessionEnd` 역시 방문 완료를 각각 증명하지 않는다.

MVP는 부탁 카드 또는 주행 종료 후 폰에서 사용자가 `바다에 다녀왔어`를 선택하면 방문을 확인한다. 모든 확인 제출에 `visitConfirmationId`를 만들고 재시도는 같은 ID를 사용한다. 연결된 주행의 세션 ID는 출처 메타데이터로만 저장한다. 한 세션에서 바다와 산을 각각 확인할 수 있으며 서로 다른 제출을 세션 ID만으로 중복 제거하지 않는다. 이 기록은 `source=userConfirmed`로 저장하며 GPS 검증이나 보호자 본인 인증이 된 것으로 표시하지 않는다.

방문 시각은 기본안에서 **확인을 저장한 시각**이다. 과거 여행 날짜 선택은 후속 확장이다. 목표 지역 확인이면 활성 부탁을 완료하고 최근 확인 시각을 갱신한다. 다른 지역 확인은 해당 지역 요약만 갱신한다. `건너뛰기`·사진 선택 취소·통신 끊김은 방문 여부를 변경하지 않는다.

사진은 완료 카드당 최대 1장을 선택적으로 붙이는 안이다. B가 촬영 또는 OS 사진 선택기를 연결한다. 취소·권한 거절·파일 저장 실패가 있어도 사진 없이 부탁을 완료할 수 있다. 사진 내용의 위치·장소를 AI로 판별해 완료를 승인하는 기능은 넣지 않는다.

사진 저장 후 캐릭터는 사진 옆에서 짧은 2D 반응과 ‘보여줘서 고마워. 함께 간 기분이야!’ 같은 검수 문구를 보여준다. 사진의 실제 내용·사람·장소를 인식한 것처럼 설명하지 않는다. 사진 없이 마친 경우에도 방문 경험을 나눠줘서 고맙다는 반응을 제공한다. 같은 사진을 다시 열 때 새로운 보상이나 부탁 완료를 중복 적용하지 않는다.

앱이 관리하는 축소본만 로컬에 저장하고, 사진·EXIF·파일 경로를 Firebase와 차량에 보내지 않는다. 복사본 생성 때 위치 등 불필요한 메타데이터를 제거하고 적용 결과를 확인한다. 사용자가 사진을 삭제하면 카드의 완료 상태는 유지한다. 사진 파일 누락·저장 공간 부족·선택 후 앱 종료에서는 사진 없는 카드로 열 수 있어야 한다. OS 사진 라이브러리 원본을 앱 삭제 동작으로 지우지 않는다.

차량의 지역 관측은 향후 ‘바다에 다녀왔나요?’라는 확인 질문의 힌트로 연결할 수 있다. 원본 위치의 신선도·도착 신호 실측이 없는 현재 단계에서 자동 방문 인증으로 확대하지 않는다.

### 7.6 장소 후보와 현재 내비

기존 `DestinationSuggester`의 고정 후보 목록·거리 계산을 재사용하되 추천 목적을 구분한다.

| 추천 목적 | 후보 지역을 고르는 기준 |
| --- | --- |
| 기존 수집 추천 | `RegionSummary`의 미수집 지역 |
| 새 여행 부탁 | 활성 `wishId`의 `targetRegion` |

바다 캐릭터를 이미 수집했어도 바다 부탁은 성립한다. 따라서 두 경로에 같은 미수집 필터를 무조건 적용하지 않는다. 현재 안내 중이라는 이유로 부탁 카드 자체를 없애지 않고 다음 여행용으로 보관한다.

- 연결되지 않은 폰에서는 캐릭터와 목표 지역, 계획·보류·완료 기능을 보여준다. 폰에 새 장소 검색 서비스를 추가하는 것은 첫 범위에 넣지 않는다.
- 차량에 연결된 뒤 사용자가 ‘부모와 후보 보기’를 선택하면 폰은 해당 세션에만 `travelRequest` 요약을 발행한다. 차량 정차 화면에서 기존 고정 장소 후보를 최대 3개 보여주는 안이다.
- 차량 위치를 사용할 수 있으면 기존 직선 120km 범위를 재사용한다. 직선거리를 도로 거리·예상 이동 시간으로 표시하지 않는다.
- 위치를 모르면 대상 지역의 고정 후보를 거리 없이 표시할 수 있다. 이때 ‘가까운 장소’라고 설명하지 않는다. 가까운 후보가 없으면 그 이유를 표시하고 부탁은 유지한다.
- 현재 대상 지역에 있으면 새 내비 제안보다 방문 확인 흐름을 우선 안내한다. 실제 방문 여부는 사용자가 정한다.
- 내비 실행은 운전자의 별도 수락 후에만 한다. 수락 직전 같은 세션·활성 부탁·대상 지역·최신 제안·`Guidance.IDLE`을 다시 확인한다.
- 기존 안내 중 또는 안내 상태 미확인이면 현재 경로를 유지한다. SDK 호출 성공은 `routeRequestAccepted` 의미이며 실제 안내 시작·여행 완료와 구분한다.
- 부탁이 완료·닫힘·다른 대상 변경되면 제안 캐시를 지우고 이전 후보 수락을 거절한다. 전체 `/game` 갱신 중에도 활성 요약을 누락하지 않는다.

## 8. 데이터와 통신 계약 제안

### 8.1 로컬 데이터

새 필드는 아래 책임으로 나눈다. 실제 파일 분리는 구현 시 결정하되 같은 상태를 여러 곳에서 독립적으로 수정하지 않는다.

| 모델 | 주요 필드 | 저장 범위 |
| --- | --- | --- |
| `IncubationRound` | `eggId`, `ruleVersion`, 기존 시간/거리 계획, `completedTopics`, `processedTurnIds`, `outcome`, 고정된 결과 | 알을 다음 주행으로 이어갈 때 유지 |

로컬 조회 실패를 ‘보유 없음’, ‘방문 없음’, ‘작업 없음’으로 바꾸지 않는다. 읽기 오류와 정상적인 빈 목록을 구분한다.

### 8.2 원격 스냅샷

계약 버전 2와 아래 추가 필드를 제안한다. 기존 필드의 의미는 유지하고 `/game` 전체 `set()` 시 항상 합성한다. 예시는 현재 새 알을 품으면서 기존 물결지기를 폰에 불러온 상태다.

```json
{
  "contractVersion": 2,
  "gameRevision": 18,
  "ts": 1794200010000,
  "eggTier": "small",
  "stage": "incubating",
  "progress": 0.4,
  "speciesId": null,
  "attribute": null,
  "tier": null,
  "careCount": 0,
  "lookOutCount": 0,
  "hatchAtM": null,
  "hatchAtSec": 300,
  "regionCollectionKnown": true,
  "uncollectedRegions": ["mountain", "city"],
  "affinity": {"score": 2, "target": 3, "ready": false},
  "companion": {
    "displayId": "display-7",
    "displayRevision": 2,
    "speciesId": "tide_keeper",
    "location": "phone"
  },
  "transferResult": {
    "requestId": "transfer-3",
    "displayId": "display-7",
    "requestRevision": 1,
    "status": "accepted",
    "resultLocation": "phone"
  }
}
```

추가 필드의 역할은 다음과 같다.

| 필드 | 내용과 제약 |
| --- | --- |
| `contractVersion` | 누락은 기존 계약. 지원하지 않는 버전의 새 기능을 켜지 않음. |
| `gameRevision` | 같은 세션 전체 상태의 정수 버전. `displayRevision`과 별개이며 오래된 원격 쓰기를 거절하는 기준. |
| `stage` | `failed` 추가 제안. 동행·거점·부탁 상태를 이 enum에 추가하지 않음. |
| `affinity` | 표시용 점수·목표·준비 상태. 원문·녹음·완료 주제 상세는 전송하지 않음. |
| `companion` | 세션 임시 표시 ID·종 ID·위치·표시 버전. 도감 원문·영속 개체 ID를 전송하지 않음. |
| `transferResult` | 요청 당시 ID/revision, 요청 ID, 확정 결과·결과 위치. 선택 없음에도 결과를 전달할 수 있는 독립 블록. |
| `baseSummary` | 역할별 종 ID와 구조물·요리·작업 종류 등 차량 표시용 최소 요약. 선택한 표시 범위가 정해지면 타입 확정. |
| `travelRequest` | 세션에 후보 표시를 요청한 `wishId`와 `targetRegion`. 방문 이력·사진·추억 전체는 전송하지 않음. |

`baseSummary`의 첫 형식은 `{builderSpeciesId?, cookSpeciesId?, trainerSpeciesId?, structureIds: string[], lastMealId?, activeTaskKind?}`를 제안한다. `travelRequest`는 `{wishId: string, targetRegion: coast|mountain|city}`다. 둘 다 생략은 표시 요청 없음으로 해석한다. Firebase가 빈 배열·null 키를 제거할 수 있으므로 `structureIds` 누락은 빈 목록으로 정규화한다. 타입 오류는 빈 정상 상태와 구분해 해당 신규 블록만 숨긴다.

### 8.3 이벤트와 결과

| 이벤트·스냅샷 | 작성자 → 소비자 | 내용 |
| --- | --- | --- |
| `companionTransferRequested` | 차량 → 폰 | `requestId`, `displayId`, `displayRevision`, `target=phone` |
| `transferResult` | 폰 → 차량 | 요청 ID·당시 표시 ID/revision과 `accepted/alreadyOnPhone/busy/staleSelection`, 현재 결과 위치 |
| 기존 `hatched` | 폰 → 차량 | 성공 저장 이후 기존 의미 유지. 실패 이벤트로 재사용하지 않음. |
| 실패 `/game.stage=failed` | 폰 → 차량 | 결과 상태 표시. 1차는 별도 실패 이벤트 없이 스냅샷으로 수렴. |
| `travelRequest` | 폰 → 차량 | 사용자가 요청한 다음 여행 후보 표시 요약 |
| 여행 후보 결과 이벤트 | 차량 → 폰 | 필요 시 `wishId`, `region`, `status=offered/routeRequestAccepted/unavailable`; 확정 전 기존 이벤트에 의미를 덧씌우지 않음 |
| 기존 `sessionEnd` | 차량 → 폰 | 최종 종료. 이동·부탁·거점 완료로 뜻을 확장하지 않음. |

이벤트는 중복되거나 유실될 수 있다. 폰 수신 어댑터는 DB 이벤트 키도 보존해 일반 중복 추적에 쓰고, 이동은 명시적인 `requestId`로 최종 판정한다. 새로운 payload의 숫자·문자열 타입을 구분하므로 차량의 기존 `Map<String, String>` 모델을 그대로 복사하지 않는다.

`by=car/phone`은 앱 간 작성 책임을 표현할 뿐 인증 증거가 아니다. 현재 DB 규칙은 세션 접근 기간과 일부 필수 키만 검사한다. 새 필드의 타입·범위·허용 상태를 규칙 테스트에 추가하되 이를 사용자·장치 인증 완료라고 설명하지 않는다. 별도 인증 개편은 이 기능 명세에서 임의로 확정하지 않는다.

### 8.4 일관된 쓰기와 버전 적용

1. 컨트롤러는 단일 쓰기 큐로 변경을 직렬화한다. UI나 대화 어댑터가 DB를 직접 쓰지 않는다.
2. 알·거점·방문·부탁 변경을 다음 로컬 상태로 계산하고 저장한다. 저장 실패면 기존 확정 상태와 오류를 보여준다.
3. 저장된 상태에서 차량 표시 스냅샷을 합성한다. 부화 시각과 이동 요청이 겹쳐도 오래된 전체 스냅샷이 새 결과를 덮지 않게 발행 순서를 고정한다.
4. 원격 발행 실패는 같은 최신 스냅샷을 재시도한다. 보상·호감도·방문 완료를 다시 실행하지 않는다.
5. 연결 세대가 바뀐 뒤 이전 비동기 저장/발행 결과가 새 세션의 성공 상태를 갱신하지 않게 검사한다.

같은 세션의 `/game`에 대해 `gameRevision`을 추가하고, 발행 예정 스냅샷·버전을 로컬에 먼저 기록한다. 재연결 시 원격 revision과 **미전송분을 포함한 로컬 최종 발급 revision** 중 큰 값보다 높은 번호로 새 스냅샷을 만든다. 같은 세션에는 한 폰의 프로필만 판정 작성자로 사용한다. 다중 폰 동시 편집은 이 계약에 포함하지 않는다.

서버 적용에서도 순서를 보호한다. 버전 2가 활성화된 세션은 현재 값보다 높은 `gameRevision`의 전체 쓰기만 받아들이도록 DB 검증 규칙 또는 동등한 조건부 쓰기를 구현한다. 낮은 버전·버전 없는 구형 쓰기는 거절한다. 같은 revision 재시도가 거절되면 서버에 이미 같은 스냅샷이 적용됐는지 읽어 확인하며, 다른 내용에 같은 번호를 재사용하지 않는다. 더 높은 버전이 있으면 과거 스냅샷을 다시 밀어 넣지 않는다. 로컬 최종 발급 기록과 원격 상태의 관계를 확인한 뒤 다음 번호를 구성하며, 원격 상태가 로컬 저장본보다 새롭거나 작성자가 충돌하면 동기화 오류로 중단한다. 제한된 차량 표시 스냅샷만으로 도감·알 진행 전체를 복원했다고 추정하지 않는다.

클라이언트 큐 취소나 Future timeout이 이미 제출된 오프라인 쓰기를 취소한다고 가정하지 않는다. 이전 set이 뒤늦게 도착해도 서버가 낮은 revision을 거절해야 T41을 통과한다. 차량은 수신 스냅샷의 revision 역행도 무시한다. 실제 DB 규칙 적용·오프라인 재접속 검증이 끝나기 전에는 이 순서 보장을 구현 완료로 기록하지 않는다.

새 게임의 `failed` 상태를 기존 차량이 정상적으로 표시한다고 가정하지 않는다. **기본 적용안은 A/B 동시 버전 적용 후 테스트 환경에서 기능을 켜는 것**이다. 구버전 차량과 연결하면 새 상태를 조용히 `hatched`로 바꾸지 않고 업데이트 안내와 원격 신규 기능 비활성 상태를 표시한다. 폰의 기존 로컬 결과는 보존한다. 구버전 판별에 필요한 앱 버전/계약 지원 값은 A/C가 정하고, 펌웨어·앱 문자열을 추측해 지원 여부를 판단하지 않는다.

### 8.5 로컬 이행과 저장 기술

기본 저장안은 버전이 있는 `LocalProfileV2` 한 묶음에 도감·알 체크포인트·개체 동작·선택·거점·여행 상태를 담는 것이다. 사진은 파일로 두고 참조만 포함한다. 기존 `DexStore` 호출부는 어댑터를 통해 이 저장본을 읽도록 바꾼다. 여러 SharedPreferences 키에 각각 쓴 뒤 하나의 트랜잭션이 완료됐다고 가정하지 않는다.

- 새 저장본 생성 전 기존 원본을 보존한다. 기존 획득 행마다 개체 ID를 한 번 부여하고 종·날짜·환경·지역·등급을 그대로 옮긴다.
- 기존 저장 대기 부화 결과가 이미 도감에 있으면 기존 행과 연결하고, 없으면 새 개체 ID를 한 번 만들어 pending 결과에 저장한다.
- 이행 결과의 버전·참조 무결성을 확인한 뒤 활성 저장본을 전환한다. 실패하면 기존 원본으로 다시 열고 신규 배치 기능을 보류한다.
- 완료 결과와 완료 ID를 같은 저장 단위에 넣어 완료 효과만 적용되고 중복 방지 정보는 빠지는 상태를 막는다.
- 실제 저장 수단은 교체 중 실패·강제 종료에 대한 복구 검증 후 선택한다. 기존 저장 API의 성공 반환만으로 전원 차단까지의 내구성을 보장하지 않는다. 결정 D10에서 단일 저장본 교체 또는 트랜잭션 지원 저장소 중 구현 범위를 확정한다.
- 이행 뒤 구버전 앱이 새 데이터를 덮어쓸 수 있으므로 구버전 앱으로의 임의 복귀를 지원한다고 약속하지 않는다. 테스트용 이전 저장본과 복구 절차를 유지한다.

### 9.1 C가 제공할 규칙 인터페이스

아래 함수명은 계약 설명용 제안이다. 실제 이름을 확정하기 전에 기존 타입과 export 구조를 맞춘다.

코어 함수는 `DateTime.now()`, 네트워크, 파일, STT, UI에 직접 접근하지 않는다. 필요한 시각·차량 판정 입력·ID를 인자로 받는다. 같은 상태와 같은 입력은 같은 결정을 내린다. 종 선택의 난수는 현재처럼 외부에서 고정 가능하게 주입하고, 재시도에는 저장된 선택 결과를 재사용한다.

## 10. 오류 처리와 검증 기준

### 10.1 공통 원칙

앱 일시중단과 차량 최종 종료를 구분한다. 저장 중 종료가 발생하면 신규 입력을 닫고 이미 결정한 결과 저장을 마친다. 복구 가능한 저장 오류를 성공으로 표시하지 않는다. 폰의 로컬 거점·부탁은 차량 연결 실패 때문에 삭제하지 않는다.

실사용 데이터를 시연 시간 압축·강제 역할 지급·Fake 날씨와 섞지 않는다. 테스트는 가짜 시계·입력·저장 실패를 주입해 경계를 재현하고, 실제 STT·Gleo·차량 제한·네트워크 왕복은 별도 단계에서 검증한다.

### 10.3 테스트 위치와 완료 판단

- 코어: 기존 `phone/packages/allo_core/test/`의 시간·거리·희귀도 테스트를 유지하고 호감도·거점·부탁의 순수 판정 테스트를 추가한다.
- 폰: 기존 `phone/test/`의 `recurring_incubation`, `session_end`, `session_resume`, `storage_failure`, `firebase_feed`, `companion` 회귀를 관련 변경 범위에서 실행한다. 입력 어댑터·스토어·시계를 교체해 실패를 재현한다.
- 차량: `GameMergeTest`, `GleoFunctionsTest`, `DestinationSuggesterTest`, `RegionSummaryTest`, `SessionEndDetectorTest`를 확장해 파싱·캐시·종료 회귀를 확인한다.
- 통합: 운영 데이터와 분리된 테스트 환경에서 실제 RTDB 왕복을 확인한다. DB 규칙 배포·운영 데이터 변경은 별도 작업으로 다룬다.
- 음성·화면: 실제 목표 기기의 입력 성공률·지연·주행 표현을 기록한다. 코어 테스트 통과를 음성/실차 검증으로 대체하지 않는다.

각 기능의 완료 조건은 **규칙 테스트 + 저장/복구 + 화면 연결 + 관련 왕복 확인**이다. Fake 입력만 연결된 기능은 ‘로직·시연 완료’로 기록하고 실제 기기 기능 완료와 구분한다.
